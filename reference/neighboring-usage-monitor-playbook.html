Architecture and workflow reference

Learn from neighboring monitors without becoming one

Borrow evidence, seams, and verification habits. Keep the product promise, data ownership, and user experience recognizably yours.

The recommendation

Keep the existing quota path intact. It asks the installed Codex CLI app-server for account and rate-limit data, validates repeated samples, and retains last-known-good results.

Add local session analytics as a separate domain only if it serves a clear user job. Start with a Codex-only “session pulse” such as last activity, today’s tokens, and active-session count. Do not pour token history into QuotaPresentation.

Use Tokscale, ccusage, and CodexBar as triangulated references and comparison oracles first. A runtime dependency should be a later, explicit product and maintenance decision.

A file watcher should only say “something may have changed.” It must not own parsing, aggregation, scheduling, or UI state. The parser should produce a deterministic snapshot whether invoked by launch, a periodic refresh, a manual action, or a watched-file event.

How Token Monitor differs today

Token Monitor’s documented collector invokes Tokscale for today, month, and all-time scans on full ticks. Watched changes trigger a cheaper today-only scan and derive longer periods from a full-scan anchor. It watches known client paths with polling and debouncing, deliberately excludes self-generated cache paths to avoid refresh loops, and reads detailed session content on demand rather than syncing it.

Your app currently has no session watcher or local token parser. Its refresh schedule is about provider quota freshness and reliability. Treating these as one subsystem would couple file churn, pricing rules, and quota notifications for no user benefit.

A stronger agent-assisted development loop

This section now has a detailed, repository-specific companion: Evidence-Rich Pull Requests. It explains the full path from problem framing through a Draft or Ready PR, including branch isolation, root-cause evidence, regression proof, signed-app acceptance, review follow-up, and rollback. Agents should use the repo-local preparing-evidence-rich-prs skill for the compact execution workflow.

  1. Frame: write the user problem and one observable outcome. Do not begin with “copy feature X.”
  2. Gather evidence: reproduce current behavior, inspect local ownership, and read two independent implementations.
  3. Generate options: include “do nothing,” a narrow native solution, and an integration. State privacy and maintenance costs.
  4. Decide: write a small ADR for architecture or data-boundary choices. Record rejected options.
  5. Probe: answer unknown protocol or file-shape questions in UsageProbe before production code.
  6. Plan a tracer bullet: source → typed contract → one presentation → acceptance. Avoid broad infrastructure first.
  7. Implement in reviewable increments: keep contracts and compatibility surfaces explicit; update the plan as evidence changes.
  8. Verify proportionally: parser fixtures and focused checks where allowed, then the signed app and manual macOS acceptance for UI behavior.
  9. Review the evidence: explain root cause, measurements, commands, screenshots, limitations, and remaining manual checks.
  10. Reflect: record one non-obvious lesson only after you can explain or apply it.

What to take from their agent setup

  • One canonical entry point: Token Monitor’s CLAUDE.md imports AGENTS.md so agents share guidance.
  • Contracts over tours: document non-obvious invariants, compatibility surfaces, and failure traps rather than paraphrasing the file tree.
  • Commands as policy: one verification command reduces handoff ambiguity; Token Monitor uses npm run verify.
  • Evidence-rich changes: PR #144 states the symptom, root cause, before/after timing, tests, and remaining work.
  • Scoped instructions: ccusage routes specialized work to repo-local skills and nearest-package AGENTS.md files.
  • Sign-off boundaries: CodexBar’s short vision distinguishes routine fixes from auth, privacy, dependency, and architecture changes.

Your root AGENTS.md already has excellent, evidence-based Settings, notification, and native-menu guardrails. The next optimization is not more root text. When a new subsystem arrives, move its durable instructions near the owning subtree or into a task-specific repo skill, leaving the root for always-on rules and routing.

Suggested feature order

  1. Finish the current Codex quota reliability and manual-acceptance gates.
  2. Survey Codex session record shapes and privacy-sensitive fields in UsageProbe.
  3. Define LocalUsageSnapshot independently from quota state.
  4. Prototype a Codex-only session pulse with bounded scanning and explicit unavailable/stale states.
  5. Add pricing only after model resolution, provenance, cache invalidation, and disagreement behavior are specified.
  6. Deepen a provider adapter seam only when a second real provider is approved.
  7. Consider sync or broad dashboard work only when it becomes a product goal, not because a neighbor has it.
